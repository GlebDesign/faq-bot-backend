# Правила учёта обращений

Основные правила согласованы 26.11.2026. Границы срока trial и резерва согласованы 27.11.2026. Баланс общий для компании. Единица баланса называется обращением. Один завершённый вызов модели расходует одно обращение независимо от числа токенов провайдера. Вызов направляется выбранному в меню провайдеру.

## Начисления

- Новая компания получает trial один раз через существующее намерение регистрации. Стартовые настройки — 25 обращений на 14 дней. Их задают `TRIAL_REQUESTS` и `TRIAL_DAYS`. Повтор обработки одного намерения сохраняет прежнее начисление.
- Купленные пакеты суммируются и не истекают. Сначала расходуется действующий trial. Среди бессрочных начислений первыми расходуются самые ранние.
- Доступный остаток — неиспользованные обращения из действующих начислений за вычетом действующих резервов, привязанных к этим начислениям.

Миграция 8 хранит доступные для покупки пакеты в `quota_packages`, начисления в
`quota_allocations`, резервы в `quota_reservations` и расход в `quota_usage_events`.
SQL гарантирует единственный trial на намерение и связывает запрос, начисление
и расход внутри одной компании. Купленное начисление хранит выданное число
обращений отдельно от текущего размера пакета. Каталог поставляется пустым.

Bootstrap выдаёт trial в той же транзакции, что и новая регистрация. Если
намерение сохранил API предыдущей версии, ближайший успешный bootstrap обработает
его один раз. Для старой компании без намерения bootstrap сохраняет прежнюю
идентичность. Срок выдачи берётся из намерения, поэтому к первому bootstrap trial
может уже истечь. Репозиторий читает остаток на момент SQL-запроса. Он вычитает
активные и списанные резервы только из действующих начислений. Активный резерв
продолжает занимать обращение до фиксации его исхода.

## Резерв и завершение

Хранилище выдаёт trial, читает остаток и атомарно резервирует обращение.
Внутренний сервис вызывает переданный адаптер после сохранения нового резерва
и сохраняет исход запроса. При запуске с Auth процесс API сразу проверяет
просроченные резервы и повторяет проверку каждые пять секунд. За проход он
загружает до 32 записей, а решение по каждой повторно проверяет под блокировкой
компании. Проход по очереди ограничен временем БД на его начало. Записи,
пропущенные из-за временной ошибки, снова проверяются в следующем проходе.
Покупка пакетов и подключение провайдера к HTTP API относятся к
следующим этапам.

Перед вызовом модели операция резервирует одно обращение. Резерв и проверка остатка сохраняются в одной транзакции, которая завершается до вызова провайдера. При остатке 1 из конкурирующих операций резерв получает только одна. При остатке 0 вызов модели не выполняется. У резерва уникальный `ai_request_id`.

| Событие | Изменение резерва и баланса |
| --- | --- |
| Чат завершился ответом или результатом `no_answer` | Резерв списывается один раз |
| Тестовый чат завершился ответом или `no_answer` | Резерв списывается по тому же правилу |
| Вызов модели в Coverage завершён | Его резерв списывается. Если вызовов несколько, каждый учитывается отдельно |
| Ошибка, таймаут или отмена | Резерв освобождается без списания |
| Повтор того же ключа в пределах того же scope | При тех же данных возвращается исходное состояние или результат. При изменении данных API возвращает 409. Новый резерв не создаётся |
| Поздний результат после освобождения резерва | Сохраняется исход ошибки, таймаута или отмены. Результат не создаёт списание |

После вызова провайдера отдельная транзакция сохраняет результат, списание и запись операции в журнале. При ошибке, таймауте или отмене отдельная транзакция сохраняет исход и освобождает резерв. Состояния списанного и освобождённого резерва окончательные. Если списание было зафиксировано, повтор возвращает сохранённый результат. Гонки восстановления, отмены и завершения дают один окончательный исход.

## Границы срока

1. Отсчитывать срок, заданный при выдаче trial, с момента записи намерения при регистрации компании. Одни сутки равны 24 часам. Задержка обработки намерения сдвигает момент доступности trial, но не дату истечения.
2. По истечении trial запретить новые резервы из него. Уже созданный резерв сохраняется до исхода операции. Если операция завершится вовремя, списать обращение из trial. Если резерв освободится, истёкшее обращение не возвращается в доступный остаток.
3. Для каждого резерва записывать отдельный дедлайн вызова. Списание допускается, только если при окончательной проверке в транзакции по часам БД дедлайн ещё не наступил. На границе дедлайна и после неё исходом становится таймаут, даже если обработчик восстановления ещё не запустился. При ошибке, отмене или обнаруженном таймауте запрос освобождает резерв сразу при сохранении исхода. После сбоя просроченный активный резерв освобождает обработчик восстановления. Поздний результат не меняет исход и не создаёт списание.
