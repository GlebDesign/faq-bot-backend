# Миграции БД

Миграция — SQL-файл, который изменяет схему БД. Сервер API не применяет миграции
самостоятельно: для этого используется программа `cmd/migrate`.

## Запуск

Сначала подготовить PostgreSQL по [DATABASE.md](DATABASE.md). Затем из `backend`
с заданной переменной DATABASE_URL выполнить:

```sh
go run ./cmd/migrate
psql "$DATABASE_URL" -c 'SELECT version, dirty FROM schema_migrations;'
```

Сейчас в `migrations` находится версия `000001_identity`. Она создаёт таблицы
`users`, `accounts`, `account_members`, `sessions`. После успешного запуска
ожидается `version=1`, `dirty=false`. Повторный запуск не меняет уже применённую схему.

Путь к SQL-файлам задаётся через MIGRATIONS_PATH, по умолчанию это `./migrations`
относительно текущей папки. Программа читает общие настройки приложения, поэтому
неверные HTTP-параметры и частично заданные настройки Auth тоже мешают её запуску.
В отличие от API, migrator не требует Auth в staging/production: если все четыре
Auth-переменные отсутствуют, достаточно `DATABASE_URL` и корректных общих настроек.
Не передавать `AUTH_ALLOW_INSECURE_HTTP=false` отдельно: даже это значение включает
проверку полного набора Auth. Роль migrator должна иметь `CONNECT` к БД,
`USAGE, CREATE` в выбранной схеме и владеть создаваемыми таблицами.
Порядок установки в `public`, отдельные роли и точный SQL выдачи прав API приведены
в [плане релиза 0.0.1](upgrade_cluster/release_0.0.1.md).

## Как добавлять миграции

Файлы имеют номер, название и окончание `.up.sql` или `.down.sql`.
Текущая пара — `000001_identity.up.sql` и `000001_identity.down.sql`.
Следующая получает новый номер. Уже применённые файлы не меняются: исправление
оформляется новой миграцией. Паролей и рабочих данных в SQL быть не должно.

`up` применяет изменение, `down` описывает откат. Программа проекта запускает
только `up`; команды отката в ней нет. Файл down может удалять таблицы и данные.
Текущий `000001_identity.down.sql` удаляет все четыре таблицы приложения, но не
обновляет `schema_migrations`. Его прямой запуск через `psql` оставит историю
несогласованной. Для отката приложения обычно достаточно вернуть предыдущий образ
и конфигурацию, сохранив БД. Разрушительный откат схемы описан отдельно в
[плане установки](upgrade_cluster/release_0.0.1.md); нужны резервная копия и остановка API.
Транзакционная миграция содержит явные `BEGIN` и `COMMIT`. Операции, которым
нельзя выполняться в транзакции, например `CREATE INDEX CONCURRENTLY`, требуют
отдельного файла и плана восстановления при ошибке.

## Если произошла ошибка

Для защиты от одновременного запуска используется блокировка PostgreSQL
на отдельном соединении. Ожидание блокировки ограничено 5 секундами,
выполнение SQL — 30 секундами. SIGTERM останавливает обработку перед следующим
файлом; текущий SQL может выполняться до таймаута.

В `schema_migrations` хранится версия и признак `dirty`. Значение `true` означает,
что применение не завершилось успешно. Автоматического сброса этого признака нет.
Сначала нужно сохранить резервную копию, проверить схему и выяснить, какие команды
успели выполниться. Простая смена версии не исправляет таблицы.

После проверки можно убрать частичные изменения и повторить миграцию либо
завершить изменение схемы вручную. Для исправления номера версии нужен отдельный
CLI golang-migrate v4 с драйверами file/postgres: встроенный `cmd/migrate` не имеет
команды `force`. Номер выбирается по фактической схеме. После исправления нужно
снова запустить миграции и проверить `version` и `dirty`.

На новой БД пустой каталог даёт пустую историю версий. На БД с применёнными
миграциями отсутствие исторических SQL-файлов считается ошибкой.
