# Правила Go-кода

Основное правило — писать код так, чтобы его было легко читать и проверять.

- В небольших функциях использовать короткие понятные имена. Сокращения писать как `ID`, `URL`, `SQL`.
- Ошибки проверять сразу и выходить из функции, чтобы не накапливать вложенные `if`.
- Не создавать интерфейсы и общие обёртки без конкретной необходимости.
- HTTP-код, логику приложения и SQL держать в своих пакетах, как описано в [ARCHITECTURE.md](ARCHITECTURE.md).
- Не использовать `panic` для обычных ошибок.

Причина ошибки сохраняется через `%w`, `errors.Join` и проверяется через
`errors.Is/As`. Ошибки драйвера БД могут содержать SQL и данные подключения.
Для них используется `db.WrapError`: сообщение остаётся безопасным, а исходная
ошибка доступна для проверки. Раскрывать её через `Unwrap` и писать в лог нельзя.

У каждой горутины должно быть понятное условие завершения. Для отмены используется
`context`. Каналы передают данные и сигналы, mutex и atomic защищают общее состояние.
Комментарии в Go-код и тесты не добавляются; пояснения хранятся в документации.

После изменения Go-кода выполнить из `backend`:

```sh
gofmt -w .
go test ./...
go vet ./...
golangci-lint run ./...
```

Настройки линтера находятся в `.golangci.yml`, используется формат v2.
Вместо отдельного форматирования доступен `golangci-lint fmt` с gofmt и goimports.
Линтер устанавливается отдельно от приложения. Для изменений параллельного кода
нужен `go test -race ./...`. Условия запуска тестов описаны в [BACKEND.md](BACKEND.md).
