# Регистрация, вход и сессии

Для проверки email и пароля используется Supabase. После успешного входа backend
выдаёт свою сессию: случайный токен в cookie `faqbot_session`. В PostgreSQL хранится
SHA-256 хеш токена. Пароль и токены Supabase локально не сохраняются.
Контракт реализован в [auth.go](../backend/internal/handlers/auth.go),
[DTO](../backend/internal/handlers/dto/auth.go) и [сервисе](../backend/internal/service/auth.go).

## Настройка

Сначала подготовить [БД](DATABASE.md) и применить [миграции](MIGRATIONS.md).
Для стенда полный порядок указан в [плане релиза 0.0.1](upgrade_cluster/release_0.0.1.md).
В отдельном тестовом проекте Supabase должен быть включён вход по email и паролю.
URL проекта и ключ API передаются через окружение; полный список, потребители
и правила проверки переменных — в [BACKEND.md](BACKEND.md).

Для текущего сценария регистрации Supabase должен сразу вернуть `user.id` и
`access_token`: подтверждение email требуется отключить. Если токена нет,
backend вернёт 502, хотя облачный пользователь уже мог быть создан.
Для стенда без писем отдельно проверить настройки уведомлений, SMTP и
восстановления пароля в Supabase. Backend эти настройки не меняет и не
реализует собственный маршрут восстановления пароля. Доступность Supabase
при старте не проверяется — только при регистрации и входе.

Пример локального запуска из корня проекта, при уже заданных `DATABASE_URL`
и `SUPABASE_KEY`; `<SUPABASE_PROJECT_URL>` заменить URL тестового проекта:

```sh
cd backend
export APP_ENV=development
export SUPABASE_URL='<SUPABASE_PROJECT_URL>'
export AUTH_ORIGIN='http://localhost:8080'
export AUTH_ALLOW_INSECURE_HTTP=true
go run ./cmd/api
```

Значение-заглушка `<SUPABASE_PROJECT_URL>` не является действительным адресом.
Разрешение HTTP подходит только для development и loopback-адресов.
Для стенда нужны HTTPS и выключенное разрешение HTTP.

## Контракт эндпоинтов

Все пять маршрутов подключаются только при включённом Auth. Без него в development
они возвращают 404; неполный набор настроек и API без Auth в staging/production
не запускаются. Поддерживаются только методы из таблицы, включая для GET:
`HEAD` не поддерживается. Неверный метод возвращает 405 с `Allow`.

| Метод и полный путь | Запрос и требования к сессии | Успешный ответ | Основные ошибки |
| --- | --- | --- | --- |
| `GET /api/v1/auth/csrf` | Без тела; cookie необязательна. При отсутствии действующей сессии создаётся предварительная | 200 `{"csrf_token":"<токен>"}` и `Set-Cookie` | 403, 429, 500 |
| `POST /api/v1/auth/register` | JSON credentials; cookie предварительной или действующей сессии, Origin и её CSRF | 201, объект session и новая cookie | 400, 401, 403, 429, 500, 502, 503 |
| `POST /api/v1/auth/login` | То же; email и пароль существующего пользователя Supabase | 200, объект session и новая cookie | 400, 401, 403, 429, 500, 502, 503 |
| `GET /api/v1/auth/session` | Без тела; cookie сессии после входа | 200, объект session | 401 для предварительной/отсутствующей/истёкшей сессии; 403, 500 |
| `POST /api/v1/auth/logout` | Тело не требуется; cookie действующей сессии, Origin и её CSRF; допускается предварительная сессия | 204 без тела, cookie удаляется | 401, 403, 500 |

Для всех POST обязательны точный `Origin: <AUTH_ORIGIN>` и непустой
`X-CSRF-Token`; токен должен совпадать с сохранённым для cookie. Нет Origin или
заголовка CSRF — 403 до проверки сессии. После прохождения проверки частоты и формата запроса неверная или
истёкшая cookie при наличии CSRF-заголовка даёт 401, действующая cookie с неверным
CSRF — 403. Для login/register неверный Content-Type или JSON могут раньше дать
400, а превышение лимита — 429.
GET допускает отсутствие Origin; если он передан, требуется точное совпадение.
`Sec-Fetch-Site: cross-site` на GET отклоняется с 403. Для GET CSRF-заголовок
не нужен. `Authorization: Bearer` вместо cookie не поддерживается.

Login/register требуют `Content-Type: application/json` (параметр charset допустим),
один JSON-объект и отсутствие неизвестных полей:

```json
{"email":"test-user@example.org","password":"replace-with-test-password"}
```

Это пример с заменяемыми тестовыми данными. Тело ограничено 4096 байтами,
email — 254 байтами и форматом адреса без отображаемого имени, пароль —
1–1024 байтами. Нарушения дают 400, в том числе слишком большое тело.
Ограничения измеряются в байтах UTF-8; Supabase может предъявлять более строгие
требования к паролю.

Объект session для login/register/session имеет следующий формат; значения
в угловых скобках заменяются реальными значениями ответа:

```json
{
  "identity": {
    "user_id": "<UUID локального пользователя>",
    "account_id": "<UUID компании>",
    "role": "owner",
    "audit_read": false
  },
  "expires_at": "<время UTC в RFC3339>",
  "csrf_token": "<токен текущей сессии>"
}
```

`role` и `audit_read` читаются из текущего членства, а `expires_at` — абсолютный
срок сессии, не срок бездействия. Токен cookie в JSON не возвращается.
Общий формат ошибок и `X-Request-ID` описаны в [HTTP.md](HTTP.md).

| HTTP-код и `code` | Значение |
| --- | --- |
| 400 `invalid_request` | Неверный Content-Type, JSON, email или длина пароля/тела |
| 401 `unauthorized` | Нет допустимой сессии/членства либо Supabase отклонил credentials/регистрацию кодом 400, 401, 403 или 422 |
| 403 `forbidden` | Нарушены Origin, Sec-Fetch-Site или CSRF |
| 429 `rate_limited` | Внутренний лимит API; есть `Retry-After: 60` |
| 500 `internal_error` | Неожиданная ошибка, в том числе хранилища; подробности клиенту не выдаются |
| 502 `provider_bad_gateway` | Неожиданный статус или некорректный ответ Supabase, в том числе отсутствие user.id/access_token |
| 503 `provider_unavailable` | Сеть/таймаут Supabase, его 429 или 5xx |

## Порядок входа и проверка запросами

1. `GET /api/v1/auth/csrf` выдаёт токен действующей сессии или создаёт
   предварительную на 10 минут и устанавливает cookie.
2. Register/login проверяет cookie и CSRF, затем обращается в Supabase:
   `POST /auth/v1/signup` или `POST /auth/v1/token?grant_type=password`.
   В запросе передаются JSON credentials и заголовок `apikey`. Таймаут — 5s,
   перенаправления не выполняются.
3. При первом входе по `auth_subject` в одной транзакции создаются локальный
   пользователь, компания и членство `owner` с `audit_read=false`.
   Повторный вход не создаёт вторую компанию.
4. Старая сессия отзывается, если ещё действует. Из параллельных входов с одной
   cookie завершиться может только один. Logout во время проверки пароля
   приводит к отказу последующего входа с отозванной cookie.
5. Выдаются новая cookie и CSRF-токен. Для logout нужен уже новый токен.

Пример ниже предназначен для запущенного локального API с
`AUTH_ORIGIN=http://localhost:8080`. Команды выполнять из любого каталога в
sh/zsh/bash; нужны curl и Python 3. Заменить email и пароль тестовыми данными
пользователя этого проекта Supabase. Временные файлы содержат секреты сессии:

```sh
umask 077
check_dir=$(mktemp -d)
curl -sS -c "$check_dir/cookies" \
  http://localhost:8080/api/v1/auth/csrf > "$check_dir/csrf.json"
csrf=$(python3 -c 'import json,sys; print(json.load(open(sys.argv[1]))["csrf_token"])' "$check_dir/csrf.json")
curl -sS -o "$check_dir/login.json" -w 'HTTP %{http_code}\n' \
  -b "$check_dir/cookies" -c "$check_dir/cookies" \
  -H 'Origin: http://localhost:8080' -H "X-CSRF-Token: $csrf" \
  -H 'Content-Type: application/json' \
  --data '{"email":"test-user@example.org","password":"replace-with-test-password"}' \
  http://localhost:8080/api/v1/auth/login
curl -i -b "$check_dir/cookies" http://localhost:8080/api/v1/auth/session
```

Ожидается 200 для csrf, login и session, если подставлены действительные
credentials. Session должен содержать identity пользователя. Для проверки
регистрации выполнить такой же POST на `/api/v1/auth/register` с новым тестовым
email; ожидается 201. Регистрация создаёт пользователя в Supabase и локальной БД.
Для выхода после **успешного** login:

```sh
csrf=$(python3 -c 'import json,sys; print(json.load(open(sys.argv[1]))["csrf_token"])' "$check_dir/login.json")
curl -i -b "$check_dir/cookies" -c "$check_dir/cookies" \
  -H 'Origin: http://localhost:8080' -H "X-CSRF-Token: $csrf" \
  -X POST http://localhost:8080/api/v1/auth/logout
curl -i -b "$check_dir/cookies" http://localhost:8080/api/v1/auth/session
rm -f "$check_dir/cookies" "$check_dir/csrf.json" "$check_dir/login.json"
rmdir "$check_dir"
```

Ожидается 204 для logout и 401 для session после выхода. При неуспешном входе
не продолжать с чтением `csrf_token` из ответа ошибки. Не смешивать localhost
и 127.0.0.1 в cookie-запросах. Для HTTPS-стенда использовать его реальный origin
одновременно в URL, настройке и заголовке Origin; запросы через прокси проверяются
по [плану установки](upgrade_cluster/release_0.0.1.md).

## Срок сессии и права

Сессия после входа действует максимум 8 часов, при бездействии — 30 минут.
Чтение действующей сессии обновляет idle-срок до меньшего из абсолютного срока
и текущего времени + 30 минут; это относится и к внутренним проверкам сессии
при csrf/login/register/logout. Предварительная сессия ограничена 10 минутами.
Проверка `/session` предварительной сессии возвращает 401 после её чтения.

Каждая проверка читает текущую роль из `account_members`. Изменение роли или
`audit_read` применяется к следующим запросам; удаление членства закрывает доступ.
Повторный вход по известному идентификатору Supabase не восстанавливает удалённое
членство и не создаёт компанию. Если членств несколько, Bootstrap при входе
выбирает первое по `account_id`; публичного выбора компании сейчас нет.

Владелец компании не является администратором платформы. Компания определяется
сохранённым членством, а не значением `account_id` из запроса.

Cookie имеет `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, без Domain;
`Expires` и `Max-Age` соответствуют абсолютному сроку сессии. Secure отключается
только для локального HTTP-origin при явном разрешении HTTP. Для HTTPS-origin
Secure сохраняется и в development. При logout сервер выдаёт пустую cookie с
истёкшим сроком и `Max-Age=0`. Истёкшие и отозванные строки сессий удаляются
при выдаче новой сессии; фоновой очистки нет.

## Ограничения

- Если Supabase создал пользователя, а локальная запись завершилась ошибкой,
  облачный пользователь останется. После устранения ошибки БД повторить вход
  с теми же данными, а не регистрацию.
- Старая сессия отзывается до сохранения новой. Если новая не сохранилась,
  старая cookie уже не работает; после исправления БД получить csrf и войти заново.
- Смена пароля или блокировка только в Supabase не отзывает Go-сессию.
  Она действует до локального отзыва, истечения срока или удаления членства.
  Самостоятельного восстановления доступа через Go API нет.
- CORS не настроен, OPTIONS не обслуживается. Браузерной странице и API нужен
  общий origin, например через reverse proxy. Пример настройки есть в плане
  установки; фактической конфигурации стенда в репозитории нет. Curl проверяет
  HTTP, но не поведение браузера.
- На IP-адрес соединения и отдельный путь допускается 20 csrf или
  10 login/register в минуту. В памяти одного процесса хранится до 4096 ключей
  лимита; при заполнении новые ключи отклоняются. Лимит не распределён между
  экземплярами и сбрасывается при перезапуске. Заголовки Forwarded/X-Forwarded-For
  не учитываются: за proxy клиенты могут делить его лимит. Session/logout
  собственного ограничения частоты не имеют.
- Удаление сессий при выдаче новой выполняется общим DELETE без ограничения
  объёма. Перед нагрузочным запуском нужен отдельный план очистки.
- Readiness=200 не подтверждает работоспособность Auth. Отдельного
  диагностического логирования ошибок Auth-запросов сейчас нет.
- Заглушка Supabase не подтверждает настоящую регистрацию и отсутствие писем;
  для этого нужен тестовый облачный проект и браузерный клиент.

Команды тестов описаны в [BACKEND.md](BACKEND.md), наблюдаемость — в [HTTP.md](HTTP.md).
