# Регистрация, вход и сессии

Для проверки email и пароля используется Supabase. После успешного входа backend
выдаёт свою сессию: случайный токен в cookie `faqbot_session`. В PostgreSQL хранится
хеш токена, а не сам токен. Пароль и токены Supabase локально не сохраняются.

## Настройка

Сначала нужно подготовить [БД](DATABASE.md) и применить [миграции](MIGRATIONS.md).
Затем создать отдельный тестовый проект Supabase с входом по email и паролю,
получить URL проекта и ключ API для заголовка `apikey`.

Подтверждение email и автоматические письма должны быть отключены. Проверить
также настройки SMTP и восстановления пароля. Backend эти настройки не меняет.
При регистрации Supabase должен сразу вернуть `user.id` и `access_token`.
Если подтверждение почты включено и токена нет, текущая регистрация не сработает.

Из `backend` в sh/zsh/bash, с уже заданным DATABASE_URL:

```sh
export SUPABASE_URL='https://project.supabase.co'
export SUPABASE_KEY='<ключ тестового проекта>'
export AUTH_ORIGIN='http://localhost:8080'
export AUTH_ALLOW_INSECURE_HTTP=true
go run ./cmd/api
```

URL и ключ в примере нужно заменить. Разрешение HTTP подходит только для локального
запуска в development. Для стенда нужны HTTPS и выключенное разрешение HTTP.
Все переменные и условия их проверки собраны в [BACKEND.md](BACKEND.md).
Доступность Supabase при старте не проверяется — только при регистрации и входе.

## Порядок запросов

CSRF-токен защищает запрос от подделки: он связан с сессией и передаётся отдельным
заголовком `X-CSRF-Token`. Origin — адрес страницы клиента: схема, хост и порт.
Для POST он должен точно совпадать с AUTH_ORIGIN.

1. `GET /api/v1/auth/csrf` возвращает CSRF-токен действующей сессии. Если её нет,
   создаётся предварительная сессия на 10 минут и выдаётся cookie.
2. `POST /api/v1/auth/register` или `/api/v1/auth/login` принимает JSON с `email`
   и `password`, cookie, заголовки Origin и X-CSRF-Token.
3. Сервис проверяет сессию и обращается к Supabase. Адаптер вызывает
   `/auth/v1/signup` для регистрации или `/auth/v1/token?grant_type=password`
   для входа. Таймаут — 5 секунд, перенаправления не выполняются.
4. По идентификатору Supabase находится локальный пользователь. При первом входе
   в одной транзакции создаются пользователь, компания и членство с ролью `owner`.
5. Старая сессия отзывается, только если она ещё действует и не была отозвана.
   Из параллельных входов с одной cookie завершиться может только один;
   если logout успел отозвать её во время проверки пароля, вход отклоняется.
   Новая cookie и CSRF-токен выдаются клиенту.
   Регистрация возвращает 201, вход — 200. В JSON есть `user_id`, `account_id`,
   `role`, `audit_read` внутри `identity`, а также `expires_at` и `csrf_token`.
6. `GET /api/v1/auth/session` возвращает данные текущей сессии.
   `POST /api/v1/auth/logout` с cookie, Origin и актуальным CSRF-токеном отзывает её
   и возвращает 204. Отозванная сессия больше не принимается.

Для login/register нужен `Content-Type: application/json` и один JSON-объект
без неизвестных полей. Тело ограничено 4096 байтами, email — 254 байтами,
пароль — диапазоном 1–1024 байта. Supabase может предъявлять более строгие
требования к паролю.

## Проверка запросами

В другом терминале из любого каталога, с `curl` и Python 3 для чтения JSON:

```sh
curl -sS -c /tmp/faq-cookies http://localhost:8080/api/v1/auth/csrf > /tmp/faq-csrf.json
csrf=$(python3 -c 'import json; print(json.load(open("/tmp/faq-csrf.json"))["csrf_token"])')
curl -i -b /tmp/faq-cookies -c /tmp/faq-cookies \
  -H 'Origin: http://localhost:8080' -H "X-CSRF-Token: $csrf" \
  -H 'Content-Type: application/json' \
  --data '{"email":"student@example.org","password":"replace-with-test-password"}' \
  http://localhost:8080/api/v1/auth/login
curl -i -b /tmp/faq-cookies http://localhost:8080/api/v1/auth/session
```

Email и пароль заменить данными тестового пользователя, созданного в проекте.
Для проверки регистрации вместо `/login` использовать `/register` и новый тестовый
email при отключённом подтверждении почты. Ожидается 200 для login, 201 для register,
200 для session с данными пользователя. Успешный вход возвращает новый `csrf_token`: для logout
подставить **его**, сохранив новую cookie:

```sh
curl -i -b /tmp/faq-cookies -c /tmp/faq-cookies \
  -H 'Origin: http://localhost:8080' -H 'X-CSRF-Token: <csrf_token из ответа login>' \
  -X POST http://localhost:8080/api/v1/auth/logout
rm -f /tmp/faq-cookies /tmp/faq-csrf.json
```

Ожидается 204. Файлы cookie содержат секрет сессии; после проверки их удалить.
Не смешивать localhost и 127.0.0.1 в cookie-запросах. 400 означает неверный
Content-Type, JSON или формат email/пароля. 401 означает неверную либо
истёкшую сессию/данные входа, 403 — нарушение Origin/CSRF, 429 — лимит запросов,
502 — невалидный ответ провайдера, 503 — недоступность провайдера. Readiness=200
не исключает эти ошибки.

## Срок сессии и права

Сессия действует максимум 8 часов, при бездействии — 30 минут. Каждый запрос
проверки сессии читает текущую роль из таблицы `account_members`. Изменение роли
или `audit_read` применяется сразу к следующим запросам. Удаление членства закрывает
доступ. Повторный вход по известному идентификатору Supabase не восстанавливает
удалённое членство и не создаёт новую компанию.

Владелец компании не является администратором всей платформы. Поле `audit_read`
по умолчанию равно false. Компания определяется сохранённым членством,
а не значением account_id из запроса.

Cookie имеет `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, без Domain.
Secure отключается только для локального HTTP-origin при явном разрешении HTTP.
Для HTTPS-origin он сохраняется даже при включённом разрешении локального HTTP.
Истёкшие и отозванные сессии
удаляются при выдаче новой сессии; отдельного фонового процесса очистки нет.

## Ограничения

- Если Supabase создал пользователя, а запись в PostgreSQL завершилась ошибкой,
  регистрация вернёт ошибку, но облачный пользователь останется. После исправления
  подключения к БД нужно повторить вход с теми же данными, а не регистрацию.
- Старая сессия отзывается до сохранения новой. Если новая не сохранилась из-за
  ошибки БД, старая cookie уже не работает. После устранения ошибки нужно снова
  получить `/api/v1/auth/csrf` и повторить вход.
- Смена пароля или блокировка пользователя только в Supabase не отзывает уже
  выданную Go-сессию. Она действует до локального отзыва, истечения срока
  или удаления членства. Самостоятельного восстановления доступа нет.
- CORS, то есть разрешения для браузерных запросов с другого адреса страницы,
  не настроен. Для браузерного клиента страница и API должны иметь общий origin,
  например через reverse proxy. Готовой настройки proxy в проекте нет.
  Примеры curl проверяют HTTP, но не браузерное поведение.
- GET csrf/session тоже возвращает 403 при чужом непустом Origin или заголовке
  `Sec-Fetch-Site: cross-site`.
- На IP-адрес и путь допускается 20 запросов csrf и 10 запросов login/register
  в минуту. В памяти хранится до 4096 ключей лимита. Заголовки Forwarded
  не учитываются, поэтому за proxy клиенты делят его лимит. Внешнее ограничение
  запросов не отменяет этот внутренний лимит.
- Проверки с заглушкой Supabase не подтверждают настоящую регистрацию и отсутствие
  писем. Для этого нужен пробный вход в тестовый облачный проект.
- Очистка сессий выполняется общим DELETE при каждой выдаче новой сессии.
  Объём удаления не ограничен; перед нагрузочным запуском нужен отдельный план очистки.
- Неожиданная ошибка хранилища возвращает 500 без подробностей; отдельного
  диагностического логирования ошибок Auth-запроса сейчас нет.
- Ограничение email и пароля в HTTP проверяется в байтах UTF-8. В OpenAPI
  `maxLength` ограничивает символы; для многобайтных значений действуют более
  строгие ограничения обработчика, указанные выше.

Команды запуска тестов описаны в [BACKEND.md](BACKEND.md).
