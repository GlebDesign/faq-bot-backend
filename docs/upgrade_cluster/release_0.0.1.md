# Release 0.0.1 — Авторизация и изоляция компаний

## Задача

Добавить вход через Supabase и локальные сессии с привязкой пользователя
к компании. Компания и права текущей сессии определяются сохранённым членством,
а не `account_id` из клиентского запроса.

## Группа разработки

- Даниил — backend: API, авторизация, локальные данные и миграции.
- Сергей — DevOps и тимлид: параметры стенда, контейнеры, Nginx и установка.

Параметры сервера, БД, сети и внешнего адреса ещё не предоставлены;
согласованная конфигурация стенда в репозитории отсутствует.

## Описание релиза

1. Регистрация и вход по email/паролю через Supabase Auth.
2. Предварительная сессия для CSRF и собственная cookie-сессия после входа;
   SHA-256 хеш токена хранится в PostgreSQL, пароль и токены Supabase не сохраняются.
3. Получение identity и отзыв сессии. Сессия после входа действует до 8 часов,
   при бездействии — до 30 минут; предварительная — до 10 минут.
4. Таблицы `users`, `accounts`, `account_members`, `sessions` и история миграций.
   Первый вход создаёт компанию и членство `owner`, `audit_read=false`.
5. Чтение текущего членства при проверке сессии, проверки Origin/CSRF,
   ограничение частоты csrf/login/register. Роль не передаётся клиентом.
6. Отдельный runner миграций и проверки startup/ready/live.

Изоляция в этой версии относится к identity и членству сессии. HTTP API Agent,
чата и документов, общая проверка доступа к таким ресурсам и интеграция с Python AI
ещё не подключены. Общего механизма RBAC/RLS этот выпуск не добавляет.

Файл с версиями сервисов: не используется. Файл с версиями ролей: не используется.
Значения `owner`/`admin` и `audit_read` — поля членства, отдельной версии у них нет.
Исходная ревизия сборки — `e758d73ef9a649459cae642f009a94c80b52a779`.
Номер 0.0.1 — обозначение карточки; существование одноимённого Git-тега
или опубликованного образа не подтверждено. Документация, добавленная позднее,
не изменяет выбранную ревизию приложения.

## Порядок установки

1. Подготовить PostgreSQL и роли API/migrator. Задать переменные окружения
   по [BACKEND.md](../BACKEND.md#переменные-окружения). В Supabase включить
   email/password и регистрацию, отключить подтверждение email.
2. Собрать образ из ревизии `e758d73ef9a649459cae642f009a94c80b52a779`
   с [backend/Dockerfile](../../backend/Dockerfile). Сохранить ID образа
   и использовать один образ для мигратора и API.
3. Отдельно выполнить [накат миграций](../MIGRATIONS.md) и выдать права API.
   Ожидаемая версия схемы — `1`, `dirty=false`. Seed-записи не нужны:
   пользователей, компании, членство и сессии создаёт приложение.
4. Запустить API с подготовленным окружением. Проверить `/health/startup`,
   `/health/ready` и `/health/live`: ожидается HTTP 200.
5. В HTTPS-прокси направить `/api/v1/auth/` на API без изменения пути.
   Сохранить Cookie, Set-Cookie, Origin и X-CSRF-Token. Клиент и API должны
   использовать один внешний origin, указанный в `AUTH_ORIGIN`.
6. Проверить [вход и выход](../AUTH.md#порядок-входа-и-проверка-запросами)
   через внешний адрес: login/session — 200, logout — 204, session после
   выхода — 401. Readiness проверяет соединение с БД, но не работу Supabase.

## Порядок отката релиза

1. Сохранить диагностику и закрыть внешний `/api/v1/auth/` либо вернуть сохранённую
   конфигурацию Nginx. На хосте Nginx из каталога его конфигурации выполнить
   следующую команду; ожидается успешная проверка/reload:

   ```sh
   sudo nginx -t && sudo nginx -s reload
   ```
2. На Docker-хосте из любого каталога остановить и удалить новый контейнер:

   ```sh
   docker stop --time 20 faq-api-0-0-1
   docker rm faq-api-0-0-1
   ```

3. Предыдущий рабочий образ не предоставлен. При первой установке без него
   API остаётся остановленным, новый маршрут — закрытым. Если это обновление,
   вернуть заранее сохранённый образ и параметры запуска, проверить его health
   и только затем переключить upstream. Универсальной команды прежней версии нет.
4. Таблицы и пользовательские данные сохранить. Пользователи Supabase также
   остаются. Автоматический down не выполнять: [down.sql](../../backend/migrations/000001_identity.down.sql)
   удаляет четыре таблицы с данными и не исправляет историю `schema_migrations`.
   Встроенный runner умеет только up. Разрушительный откат схемы или восстановление
   копии — отдельное решение по [инструкции](../MIGRATIONS.md#новые-миграции-и-откат);
   восстановление теряет записи после копирования и не откатывает Supabase.

## Новые/изменённые эндпоинты

| № | Метод, путь | Query | Описание | Доступ (хэдеры, роли) |
| --- | --- | --- | --- | --- |
| 1 | GET `/api/v1/auth/csrf` | Не используются | CSRF и предварительная сессия | Вход не нужен; cookie необязательна; Origin отсутствует или точно AUTH_ORIGIN; Sec-Fetch-Site не cross-site |
| 2 | POST `/api/v1/auth/register` | Не используются | Регистрация и вход | Действующая предварительная/авторизованная cookie, точный Origin, X-CSRF-Token; Content-Type: application/json; роль не задаётся клиентом |
| 3 | POST `/api/v1/auth/login` | Не используются | Вход | Те же cookie/Origin/CSRF/Content-Type; credentials пользователя Supabase |
| 4 | GET `/api/v1/auth/session` | Не используются | Identity и срок сессии | Cookie после входа; Origin отсутствует или точно AUTH_ORIGIN; Sec-Fetch-Site не cross-site; текущая роль читается из членства |
| 5 | POST `/api/v1/auth/logout` | Не используются | Отзыв сессии | Действующая cookie, включая предварительную, точный Origin и её X-CSRF-Token; отдельной роли не требует |
| 6 | GET, HEAD `/health/startup` | Не используются | Начальная настройка | Без авторизации, cookie, Origin/CSRF и ролей |
| 7 | GET, HEAD `/health/ready` | Не используются | Готовность и Ping БД | То же |
| 8 | GET, HEAD `/health/live` | Не используются | Ответ HTTP-процесса | То же |

Auth-маршруты доступны при полном Auth-наборе настроек; без него в development
возвращается 404, а staging/production API не запускается. Health доступны всегда
при работающем сервере и появились до Auth-изменений. Cookie называется
`faqbot_session`; Bearer вместо неё не поддерживается. Ни owner, ни admin не
требуются как отдельный фильтр доступа к этим пяти маршрутам.
Полные форматы, ответы и ошибки — в [AUTH.md](../AUTH.md#контракт-эндпоинтов)
и [HTTP.md](../HTTP.md#проверки-состояния).

## Новые и изменённые настройки

Defaults ниже относятся к прямому запуску. Dockerfile задаёт production,
`:8080` и `/migrations`. Все переменные читает окружение процесса;
полный справочник — [BACKEND.md](../BACKEND.md#переменные-окружения).

| Настройка | Тип | Обязательное (по умолчанию) | Пример | Описание |
| --- | --- | --- | --- | --- |
| APP_ENV | enum | Нет (`development`) | `production` | development/staging/production; вне development нужна БД, API дополнительно требует Auth |
| HTTP_LISTEN_ADDR | host:port | Нет (`127.0.0.1:8080`) | `:8080` | API; host пустой, IP или localhost, порт 1..65535; migrator валидирует |
| HTTP_SHUTDOWN_TIMEOUT | Go duration | Нет (`10s`) | `10s` | Завершение API, >0 и ≤1m; stop timeout контейнера должен быть больше |
| DATABASE_URL | DSN/string | Да для установки Auth и runner (нет) | `postgresql://REPLACE_ROLE:REPLACE_URL_ENCODED_PASSWORD@REPLACE_DB_HOST:5432/REPLACE_DB_NAME?sslmode=verify-full` | API/migrator используют одну БД, разные роли; TLS/CA по стенду |
| MIGRATIONS_PATH | string/path | Нет (`./migrations`) | `/migrations` | Runner; относительный путь от рабочего каталога, пустое значение запрещено |
| SUPABASE_URL | URL/string | Да при Auth (нет) | `https://REPLACE_PROJECT_HOST` | HTTPS без credentials/query/fragment и пути; конечный `/` допускается |
| SUPABASE_KEY | string | Да при Auth (нет) | `REPLACE_SUPABASE_API_KEY` | Непустой ключ проекта для apikey; тип ключа кодом не проверяется |
| AUTH_ORIGIN | URL/string | Да при Auth (нет) | `https://REPLACE_PUBLIC_HOST` | Точный origin без пути/завершающего `/`, query и fragment; нужен общий origin клиента и API |
| AUTH_ALLOW_INSECURE_HTTP | bool | Нет (`false`) | `false` | true только development и loopback HTTP; для стенда не задавать либо false вместе с полным Auth |

Любая из четырёх Auth-переменных, даже явно заданная `false` или пустая,
включает проверку полного набора SUPABASE_URL/KEY, AUTH_ORIGIN и DATABASE_URL.
Для мигратора Auth не требуется, если все четыре переменные отсутствуют.
Пустые/неверные HTTP-настройки также могут остановить migrator.
TEST_DATABASE_URL — только настройка тестов, для установки не требуется.
