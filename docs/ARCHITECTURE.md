# Как устроен backend

Go-модуль находится в папке `backend`. У него две программы:
`cmd/api` запускает HTTP-сервер, `cmd/migrate` применяет изменения схемы PostgreSQL.

## Папки

Все пути ниже указаны относительно `backend`.

| Папка | Для чего нужна |
| --- | --- |
| `cmd/api` | Читает настройки, подключает БД и запускает сервер |
| `cmd/migrate` | Запускает SQL-миграции отдельно от сервера |
| `internal/config` | Читает и проверяет переменные окружения |
| `internal/handlers` | Принимает HTTP-запросы и формирует JSON-ответы |
| `internal/handlers/dto` | Содержит структуры запросов и ответов |
| `internal/service` | Выполняет регистрацию, вход и проверку сессий |
| `internal/repository` | Читает и записывает данные через SQL |
| `internal/models` | Описывает пользователя с правами и сессию |
| `internal/authprovider` | Обращается к Supabase для проверки email и пароля |
| `internal/db` | Настраивает соединения с БД и выполняет транзакции |
| `internal/migration` | Применяет SQL-файлы и следит за версией схемы |
| `migrations` | Содержит SQL-файлы |
| `internal/jobs`, `internal/messaging` | Содержат типы сообщений и отдельные правила обработки заданий; сервер их пока не вызывает |

## Как проходит вход

```text
Клиент → HTTP-обработчик → сервис авторизации → Supabase
                                  ↓
                             SQL-репозиторий → PostgreSQL
```

Обработчик проверяет формат запроса, Origin и CSRF-токен. Сервис проверяет
предварительную сессию и передаёт email с паролем в Supabase. В ответ получает
идентификатор пользователя у провайдера — `auth_subject`.

При первом входе в одной транзакции создаются пользователь, компания и членство
с ролью владельца. Транзакция позволяет либо сохранить все три записи, либо
отменить их при ошибке. Повторный вход не создаёт вторую компанию.

Клиент получает токен сессии в cookie, а в JSON — идентификаторы пользователя
и компании, роль, CSRF-токен и срок действия. Пароль и токены Supabase в БД
backend не записываются. При следующей проверке сессии права читаются из PostgreSQL.

HTTP-обработчик не выполняет SQL. Работа с таблицами находится в репозитории,
порядок действий — в сервисе. Конкретные зависимости связываются в `cmd/api`.
Это помогает отдельно проверять HTTP, логику входа и работу с БД.

Python-модуль `ai` запускается отдельно. Go-сервер к нему не обращается.
Доступные маршруты перечислены в [HTTP.md](HTTP.md), запуск — в [BACKEND.md](BACKEND.md).

## Отдельные правила заданий

В исходниках есть функции, которые можно проверить без RabbitMQ:

- `messaging.Route` выбирает точку отправки и ключ маршрута сообщения.
- `jobs.CanTransition` проверяет, допустим ли переход между состояниями.
- `jobs.DecideResult` сравнивает задание и результат по компании, агенту,
  версиям и попытке. Возвращает `apply` (применить), `stale` (устарел),
  `duplicate` (повтор) или `reject` (отклонить), но ничего не записывает в БД.

Проверка сборки этих пакетов из `backend`:

```sh
go build ./internal/messaging ./internal/jobs
```

Эти функции ещё не подключены к обработке HTTP-запросов.
Перед подключением нужно согласовать получение исходных данных для Python,
количество вопросов Coverage в REST и AMQP, отображение кодов ошибок и переходы
ресурса при раннем результате задания и повторной индексации. Текущая проверка
результата допускает ресурс в `pending`, тогда как автомат состояний требует
промежуточного состояния. Применять эти правила к данным без согласования нельзя.
